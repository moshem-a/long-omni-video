Generative Video · System Design

Building a bring-your-own-key AI video studio: from casual clips to a 60-second character-consistent film

A deep dive into the architecture behind an app that both edits raw footage into a polished video and generates a minute-long video where one person stays visually and vocally identical across every shot — powered by Gemini, Gemini TTS, FFmpeg, and Gemini Omni 1.1.

There are two hard problems in "AI video." The first is making a rough, rambling recording feel professional. The second — much harder — is generating a coherent minute of video in which the same character keeps the same face and the same voice from the first frame to the last. This app does both, and it does it with a key idea that turns out to be more product decision than model trick: every user brings their own API key.

Two modes, one pipeline

The app has a single wizard UI with a mode switch at the top:

  • Edit an upload. You drop in a 1–15 minute talking-head or screen recording. Gemini watches it at 1 fps, transcribes the speech, flags filler / silence / off-topic segments, and rewrites the script while preserving your meaning. You pick a professional TTS voice, and FFmpeg reassembles a clean MP4 — captions and music optional.
  • Generate a video. You describe a concept ("a friendly barista shares three tips for better coffee"), choose a cast (invent a synthetic character or upload 1–3 reference photos), and the app plans a storyboard, generates each shot with Gemini Omni 1.1, narrates them with one locked voice, and stitches a ≤60-second film.

Both modes share the same authentication, per-user encrypted keystore, job queue, durable history, Cloud Storage, TTS, and FFmpeg assembly stage. Only the "front half" of the pipeline differs.

The product decision that shapes the architecture: bring your own key, no login

Most AI demos put the developer's API key on the server and eat the cost. That does not survive contact with "open it to everyone in the world." So the app flips it: there are no accounts at all — each visitor pastes their own Gemini API key, free from aistudio.google.com/apikey. The key is kept in the browser's localStorage, sent with each request, and the server never stores it.

This has three consequences that ripple through the whole design:

  • No shared quota or bill. Usage is billed to whoever runs the job. The app can be genuinely public.
  • Nothing to secure at rest. Because the key lives on the user's device and is transmitted per request, there is no server-side keystore, no encryption secret, and no database of user secrets to leak. The server holds the plaintext key in memory only, for the life of a single job, then drops it.
  • No accounts needed. A random per-browser id (x-client-id) is enough to scope each browser's job history — no sign-up, no password, no identity provider.
Security note. The key is never written to disk, never logged, never persisted onto the job record, and never mirrored to the database. It arrives in the x-gemini-key header, is attached to the in-memory job for the duration of the run, and is discarded. The user can remove it from their device at any time with one click.

No login at all

Dropping accounts collapses a whole layer of the system. There is no identity provider, no session, no token verification — the "auth" middleware does one small thing: it reads the caller's key and a per-browser id off the request headers and hangs them on req. Everything downstream — the job queue, the pipeline, the history — only ever sees a plain req.apiKey and req.uid.

export function attachIdentity(req, _res, next) {
  // The browser holds the user's Gemini key and sends it per request.
  req.apiKey = (req.headers['x-gemini-key'] || '').trim() || null;
  // A random per-browser id scopes this browser's job history. No login.
  req.uid = (req.headers['x-client-id'] || '').trim() || 'anon';
  next();
}

Saving a key is just a validation round-trip: the browser posts it once, the server calls Gemini to confirm it works, and on success the browser stores it locally. The server keeps nothing.

Edit mode: the sync trick

Replacing a rambling voice track with clean TTS creates an obvious problem — the new narration is a different length than the original speech, so lips, cuts, and captions drift out of sync. The fix is structural rather than clever:

Each kept segment's video is time-stretched (FFmpeg setpts) to match the exact length of its freshly generated TTS audio. Voice, visuals, and captions then line up by construction, segment by segment, before anything is concatenated.

The pipeline is a series of serialized stages — probe → analyze → plan → tts → captions → assemble — with each kept segment cut, its script re-voiced, its video fit to that audio, and the whole thing concatenated and muxed with optional captions and background music.

Generate mode: making a minute out of many short shots

Gemini Omni 1.1 (gemini-omni-1.1-flash) generates short video clips via a POST /v1beta/interactions call. A full minute isn't a single call — it's a sequence of short shots that we stitch. That means the interesting engineering is entirely about consistency across independent generations.

1. Plan the film first

Before generating a single frame, Gemini writes a storyboard: an ordered list of shots that sum to your target duration, each with a self-contained visual prompt, a narration line, and a duration. Crucially, every shot's prompt embeds the locked character description, so identity survives even in a shot generated in isolation. The storyboard is editable — you can rewrite any shot's visuals or narration, and regenerating a single shot re-runs just that one.

2. Carry identity three ways at once

The Omni docs give no explicit "lock this character" guarantee, and referencing across multiple generated videos isn't supported. So the app doesn't rely on any single mechanism — it stacks three:

  1. The same subject-reference images on every shot. Whether you uploaded photos or the app generated a synthetic keyframe (via the image model), those exact reference images are re-sent with every shot.
  2. The character description embedded in every prompt. Text describing the person rides along in each shot's visual prompt.
  3. Task-appropriate generation. Each shot uses the right Omni task — reference_to_video when subject refs drive it, image_to_video when a keyframe drives motion, text_to_video otherwise.
A real constraint I hit in production. Omni rejects previous_interaction_id whenever a video task is set — the two are mutually exclusive (a live 400: previous_interaction_id is not allowed when video task is set). Since every shot sets a task, the app can't lean on stateful chaining for continuity. Identity therefore rests entirely on the three mechanisms above: same reference images, same description, right task — a good reminder that consistency in generative video is a systems property, not one API parameter.

3. Lock the voice by owning the audio

Omni regenerates audio per interaction, and voice editing isn't supported — so across shots the voice would drift. The app sidesteps this entirely: it discards Omni's audio and lays down its own narration with a single Gemini TTS voice you pick once. In the assembly stage, each shot's video input is muxed with only the TTS track (the shot's own audio is dropped), and the video is time-stretched to the narration length — the same sync trick from edit mode, reused. One voice, start to finish, by construction.

4. Stitch and finish

Each generated shot is downloaded (720p+ clips come back as a Files API URI you poll until ACTIVE, then download), stored in Cloud Storage, narrated, time-stretched, concatenated, and muxed with optional captions and music — producing one downloadable MP4, saved to your durable history in either 16:9 or 9:16.

Durability without a database write per frame

Cloud Run instances are ephemeral and the job store is in-memory for speed, so job state is mirrored to Firestore — but carefully. Only meaningful state transitions are mirrored (job created, storyboard saved, a shot's status changing, job done), not per-shot progress ticks. That keeps a full generate job to roughly 8–12 Firestore writes while still surviving a redeploy mid-render. Any field that must persist has to be added to both the Firestore allow-list and the "should mirror" predicate — a trap worth stating out loud, because a field in one but not the other silently fails to survive a restart.

Responsible-use guardrails

Generating video of real, recognizable people is powerful and easy to misuse. The photo-upload path requires an explicit consent checkbox ("I have the right to use these images and everyone shown has consented"), warns against creating videos of real people without consent, and notes that uploading recognizable-people photos is restricted in the EEA, Switzerland, and the UK — steering those users to the invent-a-character path instead.

What I'd take away from this

The flashy part is a model that turns a sentence into video. But the parts that make it a product are the unglamorous ones: a no-login, bring-your-own-key model that lets strangers pay their own way with nothing to secure at rest, a sync trick that makes voice and picture line up by construction, and a consistency strategy that stacks three weak guarantees into one strong-enough result. Generative video, in practice, is less about the single magic call and more about the system you wrap around it.
